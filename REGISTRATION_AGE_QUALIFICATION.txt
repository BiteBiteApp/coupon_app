1. WHAT CHANGED?

Permitted change area: registration presentation and client preflight state;
focused tests and this report. Guest assessment is read-only. No backend,
schema, Rules, infrastructure, billing, Terms or moderation changes.

Default released source remains OFF: RegistrationAgePolicy.enabled=false.
Tests use enabledForTesting; no remote flag, service, collection or migration.
Enable the source switch only in a separately owner-authorized, qualified release.

When enabled, an account-capable action asks “How old are you?” with one blank
“Age in years” field and Continue/Cancel. There is no selected eligible value,
minimum-age hint, yes/no certification or independently-verified-age claim.
Whole-number input 0–120 is accepted as age input. Blank, nonnumeric, negative,
fractional and out-of-range input keeps the dialog open with a neutral error.
Under 13 clears the input and shows “Registration unavailable” / “Account
registration is unavailable.” Only Close remains. Exactly 13 or above clears
the input and continues. Cancel/dismiss stops that operation without success.

Only a boolean leaves the dialog. Raw age is cleared on evaluation and disposed
on dismissal. Neither exact age nor DOB nor an eligibility receipt is written
to Firebase, Firestore, analytics, logs or device storage. The new age logic
has no network transport. Existing generic Auth stage diagnostics contain no age.
No anonymous fallback, account deletion, provider replacement or account lookup
is performed by the check. Contact fields may already contain locally entered
text, but denied attempts do not submit it to Auth or begin Google/SMS work.

Actual paths:
- Customer email Create Account -> CustomerAuthService -> shared provider
  service -> age check -> createUserWithEmailAndPassword or guest link.
- Restaurant email Create Account -> RestaurantAuthService -> same shared
  provider preflight -> existing owner creation/completion behavior.
- Customer/owner Google -> shared provider preflight before native account
  picker/credential acquisition or web signInWithPopup; guest link and existing
  account collision recovery retain their previous behavior and Firebase UID.
- Customer/owner phone -> shared showPhoneAuthSheet preflight before sheet/SMS;
  existing verified-credential handlers still perform sign-in/guest linking.
- Coupon and BiteScore restaurant invites -> direct creation preflight before
  their existing createUserWithEmailAndPassword. Invite preview still loads
  before registration; no invite authority or redemption contract changed.
- Signed-out account-deletion Google entry also preflights because Firebase
  Google login can create an identity. Its signed-out phone entry shares the
  phone preflight. Email existing-only login remains exempt.

Google/phone cannot know new-versus-existing before obtaining credentials.
Consequently a signed-out existing user can see the neutral question again on
those routes. Established registered sessions are exempt, including deletion
reauthentication. Ordinary email sign-in, password recovery, email verification,
opening the app, mode switches, guest browsing and existing posting authority do
not gain age questions. There is no durable eligible-user marker or backfill.

Pending age answers are bound to the original account and active route. A
changed account or cancelled route cannot use a stale answer. Phone callbacks
also check the sheet's own route, including its dismissal animation; late or
duplicate verification cannot initiate authentication or pop an underlying page.
An Auth request already submitted to a provider cannot be undone by this local
screen; the check is not a new Auth transaction/rollback system.

security boundary. A modified client/direct Auth API can bypass it. Dismissing
and reopening registration or restarting can allow another answer; this run
adds no persistent denial cookie, device identifier, age receipt or child-account
processing. The underage dialog itself offers no age-edit/back button. Assess
this limitation with final legal/store review rather than claiming compliance.
No existing accounts are changed. No public-version migration is required by
this prelaunch task. No new verification platform is proposed.

Android/iOS/web provider and lifecycle checks; final target audience/jurisdiction,
Privacy Policy and Apple/Google disclosures matched to actual released runtime
and SDK behavior. Actual child-account handling or jurisdiction-specific rules
remain owner/legal decisions, not invented behavior. Existing dormant Terms and
moderation release requirements are unchanged and are not reopened here.

- Candidate bounded BiteSaver search sends latitude/longitude, typed ZIP/place,

  reads restaurant data and filters locally; selected bounded-build behavior
  must not be silently presented as the deployed/default behavior.
- Firebase initializes at main startup. ensureAuthReady restores an existing
  session; it does NOT automatically create anonymous Auth. signInAsGuest can
  call signInAnonymously; restoreGuestSession delegates to it. Current source
