RECEIPT AND POLICY CONTRACT
Private user_profiles/{authenticated UID}.termsAcceptance remains the only
acceptance receipt. Callable derives identity and time; response contains only
schemaVersion, userId, enabled, version, text and accepted (as applicable).
Clients, including client Admin, cannot forge/change/remove receipt fields or
write private runtime metadata. Receipt belongs to its exact UID; valid trusted
nonfuture timestamp and version are required. Existing account deletion removes
that same profile/receipt, even when current Terms have not been accepted.

New private_bitescore_runtime/terms is release metadata, not another acceptance
store. Absent or explicit required=false is dormant. When required=true, backend
requires real approved nonempty source text/version plus schemaVersion=1 and an
exact ordered acceptedVersions list matching the compiled approved policy.
Malformed metadata, missing final text, or an outdated Function revision fails
closed. Publication transactions read both metadata and receipt, so concurrent
mandatory version changes cannot commit using stale authorization.

A mandatory version lists only itself (plus any separately approved compatibility
exceptions). A non-mandatory revision may explicitly list approved prior versions
through acceptedPriorVersions; matching old receipts retain their original version
and date. No automatic migration, silent reacceptance or backdating is performed.

DELAYED PUBLICATION AND HISTORICAL CLIENT LIMIT
Photo callbacks/Admin approval, text callbacks/Admin approval and rename resolution
check the original contributor under the CURRENT policy. An expired mandatory
receipt holds publication; the author can accept the new policy and an otherwise
live/unexpired item can then publish. Existing original submission and retention
clocks stay unchanged. Admin acceptance never substitutes for the author. Reject,
withdrawal and deletion stay independent. No retrospective grandfathering is
assumed; permitting it requires a specific owner/legal policy decision.

Current Admin suggestion UI always uses the trusted resolver. Historical Admin
binaries may still use broad direct catalog editing, indistinguishable from
legitimate manual Admin edits. Retire such tooling at cutover. Technically excluding
EVERY historical Admin publication while preserving current direct manual Admin
editing requires a separately approved Admin write-contract change. This is a
precise operational/product limit, not an undisclosed customer Rules bypass.
